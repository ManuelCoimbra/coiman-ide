# Finish the basics, then out-Rust everyone

Rust Code has already built the things that are hard to retrofit: sandboxed WebAssembly plugins with signed registries, consent before any download, no telemetry, a built-in debugger, a test explorer and fidelity-tested modal editing. Its largest gaps are ordinary, not exotic, and a source check found that the research notes understated them. **There is no find-and-replace outside Vim's `:s`, no split editor panes, no bracket auto-close, no configurable indent width, no create, rename or delete in the Explorer, and no inlay hints or semantic tokens.** Across every editor family, users like speed, working defaults and integrated tools. They dislike imposed AI, silent network activity, forced UI change, surprise bills and unsandboxed extensions, and they ask mostly for configurability and workflow, not intelligence. Rust Code already answers about 10,900 upvotes of VS Code's top open requests, and its privacy and plugin model answer the 2025-2026 scandals directly. The best differentiator is a Rust-specific cockpit no general editor has shipped: visible rust-analyzer health, lock-contention handling, build-time explanation, `Cargo.toml` intelligence, debugger values that work, and overlays that VS Code's decoration API limits. One security gap should come first. **A cloned repository's `.rust-code/settings.toml` can set the language server command with no trust prompt.** Demand evidence is uneven: issue votes and install counts are solid, Reddit and Hacker News sentiment is anecdotal, and no survey ranks editor features.

Three other items change what can honestly be claimed. **Accessibility is a flag, not a feature**: `accesskit` is enabled on eframe, but no Rust source mentions it, so the custom editor surface is probably invisible to screen readers. **The Linux build is unproven**: eframe has default features off and `Cargo.toml` lists neither `wayland` nor `x11`, and paths in the docs are Windows-first. There is no CI folder and releases are unsigned, as `PRIVACY.md` itself admits. **Vim fidelity is real but narrow**: the golden files hold 59 Vim and 18 Helix cases. Zed's Vim mode documents surround, sneak and jump labels that Rust Code lacks ([Zed docs](https://zed.dev/docs/vim)).

The earlier research roadmap for this project was largely executed, which makes the leftovers telling. Column select, inlay hints, semantic tokens, macro expansion and line staging were all on its near-term lists and did not ship. The team built whole subsystems while small daily-use items slipped.

Measured here, `cargo bench -p rust-code-core --bench editor -- --quick` on this machine gave **0.62 ms p99 for edit plus visible highlight, 0.65 ms p99 for incremental reparse and 17.23 ms p99 for Quick Open over 100k files**, all passing their targets. Opening a large log misses its target: 123 ms for 64 MB, projected to 3.9 s for 2 GB against a 1 s goal, and the harness marks it a known gap. Startup and idle memory were not measured, because that script opens the GUI, and the script flags both as tracked gaps. These are headless numbers on one machine, not keystroke-to-photon latency and not a comparison with rivals.

## Rust Code can beat everyone on Rust's measured pain, not on features in general

The strongest evidence concerns waiting and resources. **55% wait over 10 seconds for a rebuild, about 87% rely on inline annotations and a third of those call annotation latency a big blocker, and over 35% call IDE and Cargo blocking each other a big problem** ([Rust Blog](https://blog.rust-lang.org/2025/09/10/rust-compiler-performance-survey-2025-results)). rust-analyzer has been reported at 12-16 GB on the Zed codebase and nearly 13 GB on about 830 dependencies, with "no complete way to diagnose memory overuse problems" ([discussion](https://github.com/rust-lang/rust-analyzer/discussions/20871); [forum](https://users.rust-lang.org/t/rust-analyzer-using-13-gib/133914)). In debugging, **slightly over 74% report poor value representation, over 55% cannot print variables, and about 81% prefer logs or prints as easier or faster** ([Rust Blog](https://blog.rust-lang.org/2026/09/07/rust-debugging-survey-2026-results/)). A native client cannot shrink rust-analyzer, so memory claims must separate editor from server. It can make the server visible, tunable and less obstructive, and no editor in this evidence markets that.

| **Build explainer** | `--timings` limited and few profile ([Rust Blog](https://blog.rust-lang.org/2025/09/10/rust-compiler-performance-survey-2025-results)) | Interactive Gantt, why-rebuilt, compare runs, drawn natively | Absent |
| **Debugger that shows values** | 74% and 55% above; enums, `HashMap` and `Vec` named | Regression-test formatters per toolchain, explain "optimized out" with a profile fix, skip rules for macros and iterators. Rust Code's README claims `Vec`, `HashMap`, `String` and `Option`; arbitrary enum coverage is untested | Partial, and the best existing lead |
| **First-class print debugging** | 81% prefer prints and logs | Parse `dbg!` output, click to source, inline values, remove all `dbg!`, compare with logpoints | Logpoints only |
| **`Cargo.toml` intelligence** | Even Better TOML 5.0M; crates deprecated; Dependi paywalls vulnerability reports | Version lens, feature list, schema completion, free advisory lens, all behind the same explicit network consent the editor uses elsewhere | Absent |
| **Macro expansion inline** | `rust-analyzer/expandMacro`; Zed uses a multibuffer ([commit](https://git.secluded.site/zed/commit/cdf7c10b57b10c47823c4f0e57d473a0dde4d238)); RustRover added a tester | Read-only inline block under the call, with fold | Absent |
| **Ownership overlay** | RustOwl about 5.2k stars and cites VS Code decoration limits ([RustOwl](https://github.com/cordx56/rustowl)) | A custom renderer can draw precise underlines. Demand is unproven: 10,080 installs | Absent |
| **Layout and crate graph views** | `viewRecursiveMemoryLayout`, `viewCrateGraph`; RUST-9329, 32 votes | Native byte map with padding and niches, interactive graph rather than SVG. Generics return nothing when selected directly | Absent |
| **Embedded** | 191 RustRover votes; probe-rs DAP exists, though its extension is alpha ([probe-rs](https://probe.rs/docs/tools/debugger/)) | Reuse the DAP client, add an RTT panel and SVD view | CodeLLDB only |
| **Test depth** | Zed's request has 891 votes, and Rust Code already ships a Rust test explorer | Add related tests through `relatedTests`, doctests, Criterion, and failure navigation. Live testing is free territory: Visual Studio's is Enterprise and .NET only ([Microsoft](https://learn.microsoft.com/en-in/visualstudio/test/live-unit-testing-intro?view=vs-2022)), though compile time is the feasibility risk | Strong base; no doctest handling found |

Beyond Rust, four positions are unusually defensible because they are architectural, and they can be proven rather than asserted.

**Quiet by contract.** One Zed user measured about 50% of a core at idle and 800 syscalls per second, against none for Sublime ([HN](https://news.ycombinator.com/item?id=47949027)). Rust Code's repaint calls read as event-driven apart from timers such as the backup interval, but that comes from reading the code, so measure idle CPU and publish it. Add a visible log of every external process and network-capable command it runs. Nobody in this research offers that, and 78.7% rate attribution important in AI output, which suggests a broader appetite for visibility ([IT Brief](https://itbrief.co.uk/story/stack-overflow-survey-shows-developers-trust-ai-with-caveats)). Note that one anecdote is not a benchmark of Zed.

**Plugins that cannot become GlassWorm.** Extensions there used transitive packs, remote payloads and credential theft ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-glassworm-supply-chain-developer-toolchain/)), and Wiz found 550+ validated secrets in extensions ([Wiz](https://www.wiz.io/blog/supply-chain-risk-in-vscode-extension-marketplaces)). Rust Code plugins have no WASI, no network, permissions per capability, signatures, a lockfile and update diffs, verified in `core/wit/plugin.wit` and the README. CSA notes that pinning alone cannot stop runtime-fetched payloads, and here the absence of network does. The catch is that an empty registry protects nobody, so ship several first-party plugins. Adding a network permission must keep per-host grants, or the advantage erodes. No independent audit exists yet.

**A stability promise.** Modern UI, New UI and Windows Notepad's feature creep all generated backlash ([digest](https://buttondown.com/weekly-project-news/archive/weekly-github-report-for-vscode-august-04-2026/); [Techzine](https://www.techzine.eu/news/devops/126504/jetbrains-users-struggle-with-transition-to-new-ui/); [The Register](https://www.theregister.com/2026/01/22/microsoft_notepad_update/)). A written rule costs little: no default-on redesigns, no commit message edits without a preview, no startup screens, and no nag. Fund and license the project openly too, because users distrust both Zed's venture funding and Sublime's licensing ([HN mirror](https://hn.svelte.dev/item/44961172)).

**Proof over adjectives.** Rust Code already has a benchmark harness. Published Zed and VS Code numbers conflict widely, from 180 MB to 600 MB for Zed alone ([Zed](https://zed.dev/compare/vscode); [Gil Ricardo](https://www.gilricardo.com/blog/zed-editor-review-2026)), and no modern independent latency study was found. A reproducible public suite covering keystroke-to-photon latency, idle CPU, RSS excluding servers, 1 GB find and replace, and Vim golden coverage would fill a real vacuum. Fix large-file background loading first, since the harness shows it missing target. The 20 GB Zed search anecdote shows what users will test ([HN mirror](https://hn.svelte.dev/item/45362425)).

The list of things to avoid follows from all of this. Do not enable AI by default, write trailers, or let features bypass a kill switch, because Zed's own flag once leaked predictions and needs tests ([Zed commit](https://git.secluded.site/zed/commit/899bc8a8fd9c82565cc1b37659b226587b699929)). Do not resell tokens through credits. Do not clone the VS Code extension API or marketplace. Do not treat "no plugins needed" as a strategy, since one Helix user left for Neovim over exactly that ([Grzybek](https://pawelgrzybek.com/from-helix-to-neovim)). Do not let basics absorb the team indefinitely, as Lapce's open issues on folding, DPI and keyboard layouts suggest they can, though its true cause of slowdown is unestablished ([Lapce](https://api.github.com/search/issues?q=repo:lapce/lapce+is:issue+is:open+sort:reactions-%2B1-desc&per_page=20)).

Several things remain unknown. No study shows which gaps would actually move users. Rust editor shares for 2025 beyond VS Code sit in charts that could not be read. JetBrains pages often returned 403, so its items rest on search summaries. Reddit was barely sampled, and evidence for hex, image and tab-group expectations is thin. Startup, idle memory and egui's RTL and shaping limits on this project were not measured.

## Conclusion

The research changes the question from "which feature does Rust Code lack?" to "what kind of gap is it?" Rust Code holds the rarest assets in this market, a trust architecture and native Rust tooling, yet would lose a ten-minute trial to the lack of replace and split view. Ordering matters more than the size of the list. A small batch of weeks-scale basics converts existing strengths into adoption, and only then does the Rust cockpit have an audience.

The novel opportunity is that the sharpest Rust complaints live between the editor and the toolchain, where nobody owns them. matklad has suggested that editors should own analyzer persistence, Cargo's lock fights the IDE, and debug formatters break silently. An editor built for one language, willing to measure and explain its own toolchain, competes on a dimension where VS Code's generality and RustRover's separate engine are both disadvantages. The workspace trust gate should land before the first public release, since a privacy-first editor cannot afford its first CVE to come from opening a repository.
